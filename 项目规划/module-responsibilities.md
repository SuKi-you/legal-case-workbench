# 法律 Agent 模块职责清单

更新：2026-11-02。状态：整体职责仍为目标设计；共用底座现已有宿主、材料/OCR、修订引用、案件管理、全案回滚及四项信息整理。本轮补齐模型与执行支持、成果整理与导出初版：会话绑定案件，模型选择已注册工具，执行检查点可恢复，补料形成后续处理，底稿支持版本差异和 Word/Markdown/JSON 导出。操作及有限验收见[终端执行与成果导出](../底座/docs/execution-and-outputs.md)。默认运行时仍装配 32 个能力，信息任务按配置额外装配 3 个能力；自我进化后置。

职责边界与操作见[loop 说明](../底座/docs/intake-loop.md)和[信息整理说明](../底座/docs/information.md)。`demo:loop` 使用 test 提供方检查循环机制；`demo:information` 以独立虚构材料实际调用模型，预期答案只用于评分。二者均不能代替真实卷宗和法律业务验收。

**这是一份整体职责清单，不代表下一步全部开发，也不代表每一行都要独立成一个插件、服务或软件包。** 多项职责可以由同一模块承担，最终拆分随最小案例验证调整。

项目主线：第一阶段完成接案与材料整理；第二阶段完成关键节点审查与准备。两个阶段均先在 IDE 中完整运行、分别验收，最后接入 Web。

已完成前两步技术验收：插件宿主、材料与 OCR，以及人工修订和固定引用。案件管理已完成 **创建独立案件 → 分案存取 → 人工进度标记与历史 → 建立全案保存点 → 预览与恢复 → 重启读回与撤销**。在此基础上，loop、结构化结果、执行快照与底稿均按案件保存并纳入全案恢复；完整接案仍需专业插件和业务任务集成。

前两步历史验收：材料/OCR 当时通过 45 项测试及实际测试图片识别；人工修订与引用随后通过类型检查、构建和当时的 78 项测试，并实跑文本编辑、连续保存和固定引用重启读回。这些是历史记录，不是本轮测试总数。真实照片复杂场景与法律业务尚未验收。

案件项目管理初版当时通过 108 项测试与 28 能力构建产物验证；随后全案回滚通过当时的 144 项测试，loop 控制通过当时的 183 项测试，均为历史验收记录，不是当前测试总数。当前结果集中维护在底座说明及信息整理说明。

## 一、共同约定与最小底座

| 部位 | 功能作用 | 主要输入 → 输出 | 何时实现 |
| --- | --- | --- | --- |
| **1. 技术接入协议** | 规定插件怎样声明身份、版本、依赖和能力，怎样接受调用、返回结果或错误，让别人有明确接入规则。 | 插件声明、能力输入输出定义 → 宿主可识别的插件契约。 | 已实现最小协议、类型与接入说明。 |
| **2. 法律协作协议** | 约定案件、材料、来源、陈述、判断、问题及其关联的含义，让法律插件之间能交换并理解结果；允许各部门法扩展专业字段。 | 不同插件的法律工作成果 → 含义一致、可继续使用的对象与引用。 | 已定义案件、材料/版本/引用，以及需求、结构化记录、关联、冲突与满足状态契约；完整法律判断、任务及变更依赖后续加入。 |
| **3. 插件宿主／薄运行时** | 按配置加载插件，查找并调用能力，检查输入输出，返回明确结果；检查依赖、版本并管理资源清理。 | 插件配置、能力调用请求 → 调用结果或错误记录。 | 已实现当前最小宿主，不包含案件任务恢复或存储。 |
| **4. 测试插件** | 提供确定性的演示能力，检验接入、调用、来源字段和错误处理；用同接口实现检验替换。 | 虚构测试材料 → 可预先核对的结构化结果。 | 已实现两种提供方及同一消费者，不承担法律分析。 |

边界：技术协议规定“怎么接入和调用”，法律协作协议规定“交换的内容是什么意思”。宿主按契约运行能力，专业规则由相应插件贡献。

## 二、入口与任务组织

| 部位 | 功能作用 | 主要输入 → 输出 | 何时实现 |
| --- | --- | --- | --- |
| **5. 应用服务接口** | 为案件管理、材料存取及后续任务提供统一入口，CLI 与最终网页复用。 | 用户操作请求 → 案件资料、办理进度、材料或任务成果。 | 已提供案件/回滚、信息整理、`createLegalAgent` 会话/恢复，以及底稿生成和导出服务；接口独立于终端与 HTTP。完整专业接案任务后续集成。 |
| **6. IDE／CLI 入口** | 在 IDE 终端接收命令、文件和回答，展示结果、等待事项与错误，支持人工核对。 | 命令、文件路径、回答 → 应用服务调用及终端展示。 | `agent` 已支持连续会话、一次性任务、恢复、离线状态/列表及明确选择附件；`outputs` 管理和导出底稿。原材料、编辑、案件和信息命令继续可用。 |
| **7. Agent 运行策略插件** | 根据任务目标、案件状态与能力结果，提出读取和补查动作；通用协调器检查来源、重复动作、预算与退出条件。 | 需求、已有记录与读取轨迹 → 下一轮动作或明确退出。 | 模型可选择工具目录中已注册的能力；底座检查参数、案件范围、重复动作和预算。整理 loop 继续协调需求、读取和复核；真实专业任务策略由后续插件贡献。 |
| **8. 任务执行记录与恢复** | 保留对话、需求、来源和提供方版本、完成步骤、待办、预算与终止原因。 | 执行中的检查点 → 持久快照、重启继续及整案保存点恢复。 | 已实现逐工具和读取/复核边界的保存恢复。已确认步骤复用，未返回的模型调用重新发起；写操作先核对提交结果，不确定时停止。预算保留，补料形成关联的后续任务。 |
| **9. 接案任务插件** | 定义接案目标、可用能力和完成条件，组织材料整理、初步问题识别、必要补充及底稿交付。 | 初始案情、材料及补充 → 接案成果与尚未明确的事项。 | 第一阶段的核心功能。 |
| **10. 节点审查任务插件** | 定义某个节点的审查目标和交付条件，组织变化分析、证明缺口核查及准备事项更新。 | 已有案件、新材料、当前节点及任务要求 → 变化清单、待复核判断和准备事项。 | 第二阶段。答辩、新证据、庭前准备为候选节点，逐个确定范围。 |

边界：宿主负责可靠调用；运行策略负责行动选择；任务插件提供业务目标与完成条件。接案与节点审查沿用同一执行机制和案件工作区。

## 三、共用案件能力

共用能力默认内置在底座中，使用者无需单独安装公共插件。以下为内部职责边界，可按实际需要组合为模块或插件；普通辅助函数不必独立插件化。

| 部位 | 功能作用 | 主要输入 → 输出 | 何时实现 |
| --- | --- | --- | --- |
| **11. 材料读取与解析** | 登记文字或照片，调用可替换 OCR，保留识别文字、位置和失败记录；识别结果标为待核对。 | 文字或图片原件 → 独立识别记录及原图关联。 | 文字、PNG/JPEG 与本地中英文 OCR 已实现；本轮在案件分区内复用。PDF/Word 本轮仅原样存取，不解析。 |
| **12. 原件、来源与材料索引** | 保存原件与来源，管理文字版本和固定版本引用，核对摘录并返回原件路径。 | 原件、识别结果或人工全文修订 → 独立文字版本与可读回核验的引用。 | 材料、修订与引用已实现；本轮增加每案材料及原始附件目录、按字节导出，技术验收通过。 |
| **13. 陈述与事实时间线整理** | 从材料中整理人物、事件、时间和当事人陈述，建立关联，标记未知、冲突和推断。 | 带出处的材料内容 → 结构化记录、跨材料关联、同义归组与冲突候选。 | 四项信息整理已有初版及有限虚构验收；底稿可展示明确日期时间线，日期不明事项单列。同名不直接合并，相对时间不猜日期；法律事实判断由专业业务复核。 |
| **14. 案件工作区** | 独立案件区域、资料、材料与附件存取、人工进度历史；建立全案保存点并支持预览、恢复和撤销，保留原件与历史。 | 案件与材料操作、保存点 → 指定案件当前视图、办理标记、变化预览与可撤销恢复结果。 | 项目管理及全案回滚已实现；全部案内写入参与版本检查，loop、结构化结果、执行快照和底稿随案件保存/恢复。完整法律判断及专业任务依赖后续加入。 |
| **15. 判断依赖与变更处理** | 记录判断依据哪些材料、规则及版本；报告变更，定位可能受影响的结果，并通知相关能力进行复核。 | 对象变更、来源依赖 → 待复核候选及变更记录。 | 接案阶段先做必要修订，第二阶段扩展。可作为工作区的一部分。 |
| **16. 争点、证明任务与材料关联** | 记录每个问题需要证明什么、哪些材料支持或反对、还有哪些缺口；让节点审查继续使用这些关系。 | 专业插件的证明要求、案件材料与判断 → 可追溯的关联和缺口。 | 接案阶段建立最小关联，第二阶段完善。专业含义由法律插件贡献。 |
| **17. 缺口核对与追问辅助** | 把专业需要与已有信息对照，检查材料是否已回答、是否存在冲突，生成有理由的补充建议。 | 专业信息需求、已有材料 → 读取覆盖、内容一致性、支持类型、满足状态及补查建议。 | 代码已实现，已完成有限的独立虚构材料验收。只在已查范围声明未找到，先查未读材料；已有陈述不因缺独立印证而被重复询问。实际专业规则仍由部门法插件贡献。 |
| **18. 成果整理与导出** | 把案件状态和专业贡献组织为可核对的底稿、材料索引、变化清单及准备事项，保留引用和未知项。 | 固定整理运行、案件目录及插件贡献 → 版本化底稿和导出文件。 | 初版已实现事实版底稿、来源附录、时间线、冲突/缺项、插件区块、版本差异及 Word/Markdown/JSON 导出；快照一致和当前分析覆盖分开标记。第二阶段继续扩展节点审查成果。 |

关键边界：

- 解析能力负责读出材料；来源管理负责定位；工作区负责统一保存，避免每个插件各自维护一份案件。
- 每案在 `dataDir/cases/{caseId}/` 下分别保存 `revisions` 资料与进度历史、`materials` 材料、`files` 原始附件。调用显式使用 `caseId`；旧全局材料不自动归案，不作为分案查询的回退。PDF/Word 等附件上限 50 MiB，只按字节存取和导出。
- `stage` 为用户自定义办理阶段，`active / paused / closed` 为人工状态；`closed` 仍可继续存取。资料与进度更新携带 `expectedRevision`，冲突明确拒绝，历史不覆盖。当前不是登录权限或云端协作系统，进度标记也不代表自动法律判断。
- 全案保存点覆盖资料、进度、材料/附件、OCR、文字版本、引用、loop、执行快照和案内底稿。回滚与自动保存点原子提交，旧预览和迟到保存被拒绝；原件与历史保留，外部副本和未提交草稿不改写。任务重启从已确认步骤继续，尚未返回的模型调用重新发起，写操作先核对结果。旧进度记录不能追溯补成完整保存点。
- 照片原件与 OCR 文字分开保存，失败后仍保留原图，重试追加记录。纯文本原文版本 ID 为 `material.id`，OCR 版本 ID 为成功的 `attempt.id`；人工修订生成新 UUID，记录基准版本、基准文字哈希、编辑者自报称呼与可选备注。修订只追加、允许分支，没有默认 `latest` 版本；本轮在各案件分区复用。
- 人工修订接口直接接收用户编辑后的全文，无需聊天转述或模型改写；IDE 的 `materials:text --case` 和草稿元数据保留案件归属。原图对照、文本框和点击保存的在线页面仍由最后 Web 阶段接入同一接口。原图和旧版本保留，原 `materials.read@1` 的 `text` 字段仍返回原文，已有引用不随修订自动改指。
- 引用保存材料 ID、文字版本 ID、UTF-16 半开范围 `[start,end)`、摘录和文字 SHA-256；读回核验后返回原件路径和指定版本。人工修订没有继承旧 OCR 行框。OCR 置信度、哈希一致或摘录匹配不等于材料真实、识别正确或法律事实成立；编辑者称呼当前为调用者自报信息。
- 法律插件说明某项信息为什么重要；共用能力检查已有信息；运行策略安排追问。字段空缺本身不是追问理由。
- 模型候选先通过精确引用与字段规范化，再由单独调用复核相关性、原文支持、角色与肯否；失败有限纠正，仍不合格就拒绝。复核不能保证没有语义错误。结构化比较保留所有出处，同名仅为候选，币种/期间/口径差异与真正不一致分开，来源标签不代表鉴真。
- 变更事件报告“什么变了”；专业能力判断“法律意义上影响什么”；任务策略安排复核。新增材料不自动胜过旧材料。

## 六、底座存在价值的检验

底座一体交付统一装配、调用与默认共用能力，专业插件复用公开契约。内部宿主负责技术调用与生命周期，共用模块负责材料等业务能力，分别测试；不再要求用户始终另插一个公共插件。若两个内部模块重复承担相同职责，继续合并边界。

当前最小验证只检查三件事：

1. 插件作者能否根据一页协议和示例完成接入。
2. 更换同接口实现，能否只改配置，保持宿主和调用方不变。
3. 宿主是否减少了重复的接入、校验和调用代码。

法律协作价值要在后续共用能力与劳动法插件共同处理接案案例时另行验证。一个测试插件通过不代表跨部门法通用已经实现。

四项整理核对、模型与执行支持、成果整理与导出已完成共用底座初版，并有有限虚构材料验收。接下来按接案案例集成劳动法专业插件与完整接案任务，之后完成关键节点审查。完整法律判断及其变更依赖仍需业务实现；共用能力完成不等于完整接案验收，也不证明跨部门法通用。
