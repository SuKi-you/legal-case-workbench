# 信息整理与核对：循环控制

按用户确认，“声明需求 → 带着需求读取 → 专业核对 → 必要补查”构成通用 loop。自我进化、提示自动优化和模型训练继续后置。本文解释控制器；其上的四项真实模型能力、操作与验收见[信息整理说明](information.md)。

示例读取插件只认识这两份固定虚构文本，输出明确声明 `usesLlm: false`。它检验插件配合和循环控制，不代表已经具备对复杂法律材料的理解能力。替换为示例的 `read-together` 策略可一轮完成，引擎与契约不变。

## 模块职责

| 模块 | 当前作用 |
| --- | --- |
| `loops/contracts.ts` | 统一需求、读取任务、选定版本、候选记录、出处、专业复核和完整运行记录的数据契约。 |
| `loops/engine.ts` | `IntakeLoop(host).run(input)` 组织独立能力调用；专业插件声明/复核，读取插件按任务返回候选；统一检查出处、调用预算与退出条件。 |
| `loops/store.ts` | `LoopRunStore(dataDir).save(run)` 按起始案件版本提交不可变运行记录；`read({caseId,runId})` 读取当前案件视图中的结果并复核来源完整性。 |
| `examples/loop-fixtures.ts` | 明确标注为测试的专业与读取提供方，不包含真实法律规则或 LLM。 |

引擎是应用层协调器，专业和读取能力通过已有 `PluginDefinition` 注册。默认运行时仍提供 32 个材料/案件能力；演示另装 3 个 test 能力。协调器按能力 ID 与契约版本调用所选实现，记录实际插件身份和实现版本。底座与专业插件无需互相声明依赖，不改变原宿主的无环依赖约束。

## 一次循环保存什么

输入显式携带 `caseId`、目标、`materialId/versionId/textSha256` 来源清单、三个能力引用及轮数/读取次数预算。只读取这些指定版本，没有自动选择的 latest。当前一轮内信息需求 ID 固定，专业复核可以调整读取指令和补查理由；出现新的需求范围时开启新运行。

读取结果区分实际检查过的来源与返回的候选记录。每条候选附指定版本中的准确摘录、UTF-16 范围和文字哈希。代码拒绝跨案/未选来源、未检查来源的引用、错摘录、错范围和切断 emoji 的边界。出处通过仅证明引用存在，语义忠实与专业重要性需另行评测。

每轮记录实际读取动作、检查来源、候选记录、全部需求的专业评估和下一轮任务。专业评估必须引用已存在的记录；不能在没有任何出处记录时声称需求已满足。相对时间、否定表达和陈述归属由读取提供方保留，通用控制器不据此认定法律事实。

## 继续与退出

| 状态 | 意义 |
| --- | --- |
| `completed` | 专业插件将全部本次需求标为满足或不适用；不等于陈述被证实或法律结论成立。 |
| `needs_review` | 仍有未解决/冲突事项，专业插件未提出进一步读取，留待人工核对。 |
| `stalled` | 提出的读取任务已经执行过，没有新动作，明确结束。 |
| `limit_reached` | 轮数或读取次数预算用完，保留已取得记录与未决项。 |

默认最多 4 轮、12 次读取，可在限定范围内配置。已执行的“需求 ID＋归一空白后的读取指令＋指定来源集合”不会重复执行，单改理由也不算新动作。任务可携带选定版本的子集，读取器只能接触本次指定范围；同指令检查另一份材料属于新动作。相同来源、摘录、陈述及结构化含义的候选去重；结构化信息模块另保留等价表达和同事件的关联，不删除原话。协议错误、提供方失败和来源变化会显式失败，不能伪装成完成。

四项信息能力在旧契约上增加可选的 `need.spec`、`finding.record`、`review.analysis` 和 `run.information`。旧 test 提供方继续可用。结构化运行会进一步核验规范字段、分析对象的引用、需求读取范围，以及“已满足”评估与分析是否相符。信息服务另设实际模型调用预算，提取、语义复核与纠正重试都计入。

这两个预算限制轮数和调用次数；插件自身仍需正确结束其调用。真实模型适配器接入时需提供网络超时、取消及相应验证，当前宿主不会强停任意插件代码。

## 与案件状态和回滚的关系

运行开始固定来源版本，能力调用之间检查案件修订号，结束时重新核验来源。独立运行按起始修订号提交；受 Agent 执行器管理时，自己的检查点保存会推进预期 CAS 版本，最终按最后确认的提交版本保存，原始输入修订号和来源仍保留在检查点。外部更新或回滚不能被当成自己的保存版本接纳。失败时不把迟到结果加入当前案件。

完成或明确退出的记录保存于 `cases/<caseId>/loop-runs/<runId>.json`，案件清单新增可选 `loopRuns` 引用及文件校验值。全案保存点覆盖这些记录；预览列出将退出或返回的运行 ID，恢复/撤销保留历史文件。旧案件和旧保存点没有此字段时按空集合处理，继续可读。

当前还提供 `LoopCheckpoint` 和 `IntakeLoop.run(input,{resume,onCheckpoint,currentCaseRevision,signal})`。声明完成、每次读取完成和专业复核后保存检查点；恢复时核对原请求、提供方版本、出处、已执行动作与原预算，跳过已完成读取。未返回的单次模型请求重新发起。终端 Agent 将这些检查点存入案内执行快照，一并参加全案回滚。输入材料改变后建立关联的新运行，保留旧记录。
