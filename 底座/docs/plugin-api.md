# 部门法插件公开接口

关键节点可通过可选的 `contributeNodeReview` 提供专业准备事项。输入包含同案的固定基线运行、当前运行和通用变化报告。输出可关联已声明的需求、前后运行记录和当前来源，越界引用由底座拒绝。插件贡献与节点报告写入同一个可回滚底稿。接入用法见[关键节点审查](../../关键节点审查与准备/README.md)。

本优化版沿用插件的 `kernel / labor / adapter` 分层。底座维护案件、材料版本、原文定位、执行预算及恢复；专业知识包维护需求、要件、条件、法源与公式。公共导入入口为 `src/plugin-api.ts`，第三方适配层集中导入这个入口。

## 注册

模块可以默认导出 `LegalAgentExtension`，也可以导出 `createPlugin({ dataDir })` 工厂。终端优先调用工厂。扩展的 `profiles` 声明可序列化需求，`reviewers` 注册按 `profileId` 对应的专业复核器，`tools` 提供工具，`contributeOutput` 提供带出处的成果区块。

同一 profile 只能有一个复核器。复核器的 ID、版本与 profile 会纳入恢复环境身份；改变专业规则后应升版本并开始关联新任务，不能把旧检查点当作新规则已执行。

## 运行服务

工具执行时使用 `context.services`：

```ts
const run = await context.services.runs.read(runId);
const opinion = await context.services.model.complete({ system, user });
```

运行读取绑定当前案件与有效视图；不能通过模型生成的案件 ID 切换范围。模型请求与规划、提取、复核共同消耗已保存的任务预算，父任务取消信号会传递给请求。工厂不取得原始密钥或绕过预算的模型句柄。

独立纯函数测试可以显式注入读取器和假模型；这不代替终端执行器下的预算、隔离、取消测试。插件是可信本地代码，同进程运行；这些接口约束不是操作系统沙箱。

## 专业复核

复核输入包含目标、注册需求、带出处记录、通用覆盖分析、来源清单与已执行读取。输出包含：

- `assessments`：每个检查的材料支持状态、记录 ID、理由。
- `actions`：具体补读、补充信息或人工核对要求，必须指向已声明需求及本轮来源。
- `decision`：继续、已准备、待补料或待人工核对。

`supported` 只描述当前材料支持某个命题；文件来源和逐字引用不等于事实真实或法律条件成立。专业结果保存在 `professionalReview`，不覆盖通用 `information`，并随运行、检查点与全案保存点保存。

补读需要稳定的检查 ID、需求和来源身份。仅更换措辞不能无限重读。出现新信息需求范围时，应注册或开启新的关联运行，不能临时编造 ID 绕过范围。

## 批量读取

profile 的 `readingMode: 'batch'` 可将同一来源的至多八条需求成组提取。每条需求必须明确回答；无相关内容返回空列表，漏答不能被标为已读。通用关联、原文引用和独立语义复核继续执行。

格式或漏答经过有限纠正仍失败时，可以拆成更小的组，最后回到原单需求提取器。来源越界、无依据字段、错误归类及语义拒绝不能借拆批绕过。所有重试、拆批、语义复核都消耗同一个模型预算。整批全部完成后才原子保存各需求台账，恢复跳过已完成批次。

`maxReads` 在逐需求模式计单项读取，在批量模式计逻辑批次；对照不能直接用这个数字宣称节省。应同时比较实际模型调用、逐需求来源覆盖数和真实 token。

## 出处、成果与边界

专业意见只能引用真实 `citation.quote` 内的片段，并保留材料与版本定位；模型 `statement` 可以概括，不能冒充原文。原始引用、文字修订和人工修改版本继续由底座保存。

成果会列出选定范围、未纳入材料、未解析附件、逐需求未读范围，以及专业待办。参数已核验与法律适用已确认分别表达。未知不能转成零金额、事实不存在或自动排除路径。

旧的逐需求 profile 和运行格式继续可读。改变读取实现或提取配置时，旧检查点可能明确拒绝恢复；保留旧记录，再启动关联新任务，而非静默复用不同语义的中间结果。
